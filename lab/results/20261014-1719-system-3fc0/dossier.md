# Dossier — 20261014-1719-system-3fc0 (lens: the whole system)

## Claim

The player's-item `pull_ships` is a read barrier (it exists so the encounter scan never reads a
certificate expired by an unresolved item), but it is **not** deletable ordering: bounding it
(6138's named fix, built here as `ES_PULL_MAX` + a held scan) **freezes the frame's horizon
outright** at 2×10⁴ belt members — measured: horizon stuck at tick 55 within 1,200 frames, while
pristine at the same scene advances (slowly, with 2,893 ms monster frames). The simple "hold the
scan, let the drain resolve" is killed in this form; the pull gates liveness, not just the scan.

## Bottleneck

`frame-cost`/`nladder`: real bodies in the flyable engine. The wave's monster frames (6138: 315–
1,213 ms at 10⁵–2×10⁵) are the next frame-path break. This run's contribution is a kill: the
cheapest named fix does not fly, with the mechanism pinned one level deeper — so the next attempt
must re-order the player's item completion, not merely bound its sweep.

## Evidence

All from `lab/results/20261014-1719-system-3fc0/` (`wave_runs.txt`, `p1.log`), regenerated by
`regen.sh` (build ~16 s; flights: the bounded arm exits on its stall in ~15 s, pristine needs the
200 s timeout on this box).

- **The mechanism, from shipped code** (`crates/universe/src/universe.rs`):
  - `resolve_body(Player)` calls `pull_ships(key, !in_root)` (~line 770): an unbudgeted loop
    resolving every ship item below the player's key, inside one item, inside one frame.
  - Its customer is the scan: `encounters_for_player` → `capture` → `binding_at(j, t)`
    (`encounter.rs:163-197`), and `binding_at` reads committed state only (`body.rs:152-161`) —
    so a read at `t` is valid only if every doll-mate's items below `t` are resolved: a read
    barrier implemented as a synchronous sweep. The scan's *answer* is already held off the
    critical path (`universe.rs:1163-1165`).
  - The out-of-root path already leaves the root's ships "to the queue... inside the frame's
    budget" on the invariant "the player reads no ship: resolving the player's item before theirs
    changes no bit" (`universe.rs:762-768`) — which is what suggested the pull could be bounded.
- **The patch** (`work/patch.diff`, env-gated, digest-neutral when unset): `pull_ships` bounded by
  `ES_PULL_MAX` items, returns completion; on truncation the player's item holds its scan
  (`ES_PULL_FORCE_SCAN` forces it for diagnosis). Builds clean.
- **The probe** (`crates/universe/examples/wave_probe.rs`): belt members, reverse L8, rtf 200,
  wall budget 12 ms, prints progress every 600 frames (worst ms, over-12 count, horizon) and
  exits on a 600-frame horizon stall.
- **Measurements** (this shared Linux box, 1 thread, < 1 GB per flight):
  - members = 100,000: neither arm reaches even a 5,000 game-s cut in 150–260 s (> 10× behind
    rtf 200); worst frame 678.9 ms seen **before** 5,000 game-s — monster frames at 10⁵ on this
    box are not confined to the first-kick wave (13,037 game-s, 6138).
  - members = 20,000, cut 5,000 game-s:
    - **pristine**: horizon advances but the flight is > 15× behind (23,400 frames for a
      ~1,500-frame flight); **worst frame 2,893.1 ms**, frames over 12 ms = 656 and climbing.
    - **ES_PULL_MAX=256 + held scan**: **horizon frozen at tick 55** within 1,200 frames
      (600-frame stall exit); worst frame 200.8 ms, over-12 = 7. The budgeted drain does not
      pick the ships the bounded pull leaves: liveness depends on the sweep.

## What would make it wrong

The kill is machine-conditional in its onset (a faster box may keep the drain ahead), but the
bounded arm's frozen horizon is a structural liveness fact, not a timing one: something the
horizon waits on is completed only by the pull (candidates: ships reaching the queue only via
`requeue` after resolution; or the player's item itself blocked behind fleet/handout loops that
assume the sweep). If the next run shows the drain can pick the orphaned ships (they are queued
at birth), the freeze is a bug in my bound's placement, and the fix revives in a stricter form —
defer the scan *with its own t*, never gate the item. Cost of adopting the kill: zero (nothing
built); the patch stays env-gated as the instrument.
