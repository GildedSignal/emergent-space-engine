# Dossier — 20261012-0311-autoresearch-3d4e

**Claim.** The orbit compiler (`crates/space` `Orbit::compile`, the plane's recompile-per-kick hot path) is already division-cheap: replacing every remaining 128-bit software division on the compile path with exact word-size divisions buys only ~3% end-to-end, because the cost is diffuse — cos's exact 13-factor product chain (~18%), the rest of the node arithmetic (~20%), and ~60% spread across band cuts, Scalar/Integral bookkeeping and knot storage; the next compile-cost lever is structural (shape reuse), not arithmetic.

**Bottleneck.** Board focus line 1, "fewer kicks per orbit … kicks dominate the engine's cost", read through the taste log's finding that the plane recompiles an orbit on ~99% of kicks: the per-kick tax is ns/compile. Expected gain when the run started: ~2× (kernel microbench showed u128 soft division at 21.8 ns vs `div_word` at 3.0 ns, `isqrt(u128)` at 74.6 ns). Measured end-to-end gain: **2.4–3.0%** — the arithmetic was not the wall. Nothing gets deleted by adopting the patch; equally, the "make the divides word-size" direction is now measured dead, which deletes the next run someone would spend on it.

**Evidence.** Machine: GitHub Actions linux runner, 8 vCPU shared; load 0.4–2.2 recorded per run; all A/B verdicts from interleaved runs at matched load (3×, medians). Release, thin-lto, RUSTFLAGS unset.

- Baseline: 16409 ns/compile (tuning: 480 keys, p ∈ [2.5, 1.3·10⁶] M, e-biased), 30004 ns (heldout: near-circular, e ≤ 0.999, compact-to-far), readout 4360/4059 ns per state.
- Kernel costs (`bench/src/bin/kernels.rs`): u128/u64 soft div 21.8 ns, `div_word` 3.0 ns, `isqrt(u128)` 74.6 ns, `cos` 38.7 ns, i128 mul 1.9 ns.
- Final interleaved A/B (patch = 4 divisions in `fast_quad` → `div_word`): tuning 15911 → 15432 (−3.0%), heldout 30489 → 29773 (−2.4%), readout −2%. Bit-identity: FNV hashes over knots/increments/crossing times/states equal pristine on both corpora (`a4ca5799aa979f44`, `34ad080fe9afcf1b`); `cargo test -p emergent-space --release` all targets green (and the isqrt tail case near 2¹²⁸ — where x/y reaches 2⁶⁴+1 — was caught by the crate's own `isqrt_is_the_exact_floor` test during round 2).
- Attribution stubs (temporary, reverted): `cos` → identity: compile −18%, readout −19%. `fast_quad` body after cos → dummy: −20%. So ~60% of compile cost lives outside the node kernel.
- Reproduce (each ≤ 60 s):
  - `cd lab/results/20261012-0311-autoresearch-3d4e/bench && CARGO_TARGET_DIR=/tmp/b cargo run --release --bin compile-bench -- tuning 8` (and `heldout 8`; and `--bin kernels`)
  - `git apply lab/results/20261012-0311-autoresearch-3d4e/work/patch.diff` from the repo root, rebuild, rerun; hashes must not move.
  - `cargo test -p emergent-space -p emergent-universe --release`

**Predictions.** `predictions.md` was written before the decisive runs. P1 (heldout −25%) **failed**: −2.4%. P2 (readout −15%) **failed**: −2%. P3 (exactness: hashes identical, tests green) **held**. P4 (post-fix residual is not division-major) **held** — the surprise is that it was never division-major to begin with: the 21.8-vs-3.0 ns kernel gap is real but divisions are only ~4 per node among ~40 arithmetic+bookkeeping operations. P5 (structural: `ShapeMemo` reuse beats ns/compile tuning) stands as the live lever.

**What would make it wrong.** A corpus that weights strong-field shapes (p < 6 M, generic `node()` path with `Scalar::sqrt` per node) or non-`word_root` panels more heavily than mine would restore `isqrt(u128)` to the hot path; there the round-2 fix (kept in `/tmp/patch_num.rs.patch`, reverted from the tree) is worth ~70 ns/hit. The 3% gain itself could drown in the runner's ±4% load noise on a worse day; the interleaved medians are the defence. Cost of adopting the final patch: 4 lines in `fast_quad`, zero behaviour change by construction (quotients < 2⁶⁴ exactly where the old code already truncated `as u64`). Fit: "The cheapest compute is compute not done" (P1) — but this run's honest lesson is the corollary: measure which compute matters before making any of it cheaper; and "Measure before claiming" (P10) — my own first attribution (divisions dominate) was wrong by 5× despite correct kernel numbers.

**The lens.** Autoresearch's local search assumes the metric's bottleneck is reachable one same-bits change at a time; it is not, here. The ~60% structural residue (knot vectors, per-band cut searches, Scalar normalization) yields only to a representation change — compiling shapes once per quantized key fleet-wide (`ShapeMemo`, already half-wired) or fusing the panel loop — which changes what is stored, not just how it is computed, and so sits outside this lens. Also missed: single-machine timing at ±4% shared-load noise makes 10%-threshold verdicts fragile; the checker should demand interleaved A/B.
