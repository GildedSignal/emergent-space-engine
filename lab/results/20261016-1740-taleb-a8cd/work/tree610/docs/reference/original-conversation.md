## **Fixed Timestep vs. Variable Timestep: Pros & Cons**

When implementing a **time system**, we must decide between a **fixed timestep** and a **variable timestep** for updates. Each approach has **trade-offs** in terms of **accuracy, performance, and scalability**.

### **1. Fixed Timestep (Recommended for Physics & Simulation)**

#### ✅ **Pros:**

* **Deterministic Simulations** – Ensures the same inputs always produce the same result, which is great for debugging and networking.
* **Stable Physics** – Eliminates instability issues caused by inconsistent frame times (e.g., jittery movement, missed collisions).
* **Easier to Parallelize** – Since updates happen in predictable increments, computations can be scheduled efficiently on multiple threads.

#### ❌ **Cons:**

* **More CPU Overhead** – If the game runs faster than the simulation update rate, we must interpolate frames, adding complexity.
* **Can Feel Less Responsive** – If the physics update rate is too low (e.g., 10 updates per second), fast interactions may feel laggy.
* **Difficult to Integrate with Rendering** – The renderer runs at an uncapped frame rate, requiring interpolation between physics steps.

##### **Approach to Fix These Issues**

* Use **interpolation**: The render thread uses the last two physics states to smoothly interpolate between them.
* Optimize with **adaptive stepping**: If there are no significant changes in an agent’s environment, we can skip physics updates for that agent.

* * *

### **2. Variable Timestep (Recommended for Non-Physics Updates)**

#### ✅ **Pros:**

* **More Responsive** – Updates happen every frame, so the game world reacts in real-time to the player.
* **Less CPU Usage in Simple Cases** – If fewer updates are needed, we only calculate what’s necessary.

#### ❌ **Cons:**

* **Inconsistent Simulations** – If the timestep varies too much (e.g., 16ms → 33ms → 12ms), physics calculations become unreliable.
* **Harder to Debug** – A simulation with variable timesteps produces different results every run, making debugging difficult.
* **Scales Poorly for Parallel Processing** – Unpredictable update intervals make it hard to distribute work across threads.

##### **When to Use Variable Timestep**

* **For AI & Rendering** – These do not require strict determinism.
* **For Networking Adjustments** – If updates must align with network packets, a variable timestep can adjust dynamically.

* * *

### **Final Decision: Hybrid Approach**

* **Use Fixed Timestep** for **physics & agent updates** (ensures stability).
* **Use Variable Timestep** for **rendering, AI, and non-physics elements** (ensures responsiveness).
* **Interpolation for Rendering** – To prevent stuttering, interpolate between fixed physics states when rendering.

## **Handling Time Dilation in a Scalable Way**

Since we are simulating **relativistic effects**, time must run at different rates for different entities based on velocity and gravity.

### **1. Relativistic Time Dilation (Velocity-Based)**

According to **special relativity**, time slows down for an object moving at a high velocity relative to a stationary observer.

The time dilation factor is:

```math
\gamma = \frac{1}{\sqrt{1 - \frac{v^2}{c^2}}}
```

where:

* **v** is the object's velocity,
* **c** is the speed of light,
* **γ (gamma)** determines how much slower time runs for that object.

##### **Computational Optimization:**

* **Approximate for Low Speeds:** If **v << c**, we can use the first-order Taylor expansion:
    
    ```math
    \gamma \approx 1 + \frac{1}{2} \frac{v^2}{c^2}
    ```
    
    This avoids computing a costly square root.
* **Precompute Values:** Store γ values for different speeds in a **lookup table**.
* **Ignore If Negligible:** If **v < 0.1c**, skip calculations, as dilation is minor.

* * *

### **2. Gravitational Time Dilation**

According to **general relativity**, time runs slower in stronger gravitational fields. The time dilation factor near a massive object is:

```math
\gamma = \sqrt{1 - \frac{2GM}{rc^2}}
```

where:

* **G** is the gravitational constant,
* **M** is the mass of the planet/star,
* **r** is the distance from the center of mass.

##### **Computational Optimization:**

* **Use Linear Approximation for Far Distances:** If **r >> Schwarzschild radius**, we can approximate:
    
    ```math
    \gamma \approx 1 - \frac{GM}{rc^2}
    ```
    
    This is much cheaper to compute.
* **Precompute Values for Planets:**  
    Instead of recalculating every frame, store a **precomputed dilation factor** per celestial body.

## **Scalability & Multi-Threading Considerations**

The **biggest challenge** is ensuring the simulation scales well as the number of agents and objects increases.

### **1. What Might Not Scale Well?**

* **Gravity Calculations:**
    * Naively computing gravity for **N** objects takes **O(N²)** operations.
    * Solution: Use a **QuadTree** (2D space partitioning) or **Barnes-Hut Algorithm** to reduce it to **O(N log N)**.
* **Collisions & Proximity Checks:**
    * Checking all agents against each other is **O(N²)**.
    * Solution: Use **spatial partitioning** (e.g., grids, BVH, or QuadTrees) to cut it to **O(N log N)**.
* **Time Dilation Updates:**
    * If thousands of objects move at different speeds, tracking their clocks becomes expensive.
    * Solution: Store **relative time multipliers** and update only when velocity changes significantly.

* * *

### **2. Multi-Threading Strategy**

Since Rust allows safe **parallel execution**, we should distribute work across multiple threads.

1. **Thread 1: Physics & Time Updates** (Fixed Timestep)

**ChatGPT:**

Yes. If by “letters” you mean the individual characters in text on a screen, there is an enormous amount of optimization hiding underneath something that looks trivial.

A letter is cheap to display because computers generally do not store or draw each visible letter as a little bitmap of pixels every time. They exploit several layers of reuse.

The first big trick is that text is usually stored as **characters, not images**. The letter `A` can be represented by a tiny integer such as its Unicode code point. So the word

`HELLO`

is essentially a short sequence of numbers, rather than five pictures.

Then comes the really clever part: **fonts**.

A font generally stores a geometric description of each glyph. For example, an `A` can be represented by a small collection of curves and line segments. The computer then rasterizes that shape into pixels at whatever size you need.

So instead of storing:

> 10,000 pixels for every possible size of `A`

you can store:

> “Here is the shape of `A`; generate the pixels from it.”

This is already an enormous compression advantage.

There is another beautiful optimization: **glyph reuse**.

Suppose a document contains the letter `e` 50,000 times. You don't want to independently compute the shape of `e` 50,000 times.

The font contains the glyph once. The text contains the character many times. The renderer can repeatedly reuse the same glyph, often using a cached rasterized version.

Conceptually:

```
text:
e e e e e e e e e ...

font:
       ↓
      [e]

renderer:
      reuse → reuse → reuse → reuse...
```

And modern rendering gets even more aggressive.

A common pipeline looks roughly like:

```
Unicode text
    ↓
text shaping
    ↓
glyph IDs + positions
    ↓
glyph cache / atlas
    ↓
GPU
    ↓
pixels
```

The **glyph atlas** is particularly important for performance. Instead of generating a texture for every character every time, the renderer can pack many previously rasterized glyphs into a texture atlas and then draw little textured quads pointing at the relevant regions.

So rendering a sentence can become something remarkably cheap:

```
character
   ↓
glyph ID
   ↓
cached rectangle in atlas
   ↓
GPU draws a quad
```

The GPU is exceptionally good at doing this millions of times.

There are also optimizations at the representation level.

Fonts can use **vector curves**, especially Bézier curves, so complicated letterforms require surprisingly little data. A glyph may be describable by dozens of control points rather than thousands of pixels.

Then there is **hinting** and rasterization optimization, where the system adjusts glyph geometry to fit the pixel grid well at small sizes rather than doing arbitrarily expensive geometry calculations.

And modern systems often use **subpixel positioning**, caching, batching, texture atlases, SIMD, GPU instancing, and other tricks.

There is an even deeper reason text is so efficient:

**letters have absurd amounts of repetition and structure.**

A game engine might have to draw millions of completely different objects.

A text renderer might encounter only a few hundred distinct glyphs.

English text is especially favorable because the effective alphabet is tiny compared with the amount of text being rendered. Even Unicode, with its enormous theoretical character space, usually means that any particular document touches only a tiny subset.

So the system gets tremendous reuse:

> **huge amount of visible information → tiny set of reusable primitives**

This is actually very close to the optimization philosophy you've been exploring with your simulation engine. Instead of representing the final phenomenon directly, you represent a **small generative substrate** and reuse it everywhere.

A letter is almost the perfect example:

> **Store the rule/shape once; instantiate it thousands of times.**

And there is one more fascinating layer: **text itself compresses extraordinarily well**. English has strong statistical regularities—certain letters, pairs, words and grammatical structures occur much more often than others. Compression algorithms exploit this, which is why a large text file can be dramatically smaller than an equivalent raw image of the text.

So there are really several distinct kinds of optimization stacked together:

**semantic compression** — characters instead of pictures  
**geometric compression** — curves instead of pixels  
**reuse** — one glyph definition used many times  
**caching** — rasterized glyphs reused  
**batching** — many characters rendered in large GPU operations  
**statistical compression** — text itself has highly predictable structure

That's why text can look visually enormous while being computationally tiny.

And this is one reason your old **Emergent Space** idea is interesting from an engine-design perspective: the same principle of **“don't store the thing, store the smallest reusable generator of the thing”** can apply far beyond fonts.

+ military weakness
+ recent conquest

local tension

# Acceleration isn't actually the quantity you want

You don't want:

# Light fits the exact same representation

This is where the architecture starts becoming unusually clean.

Matter follows timelike worldlines:

```
          future
            │
          ship
           /
          /
---------*---------- space
```

Light follows null worldlines:

```
        \   /
         \ /
          *
         / \
        /   \
```

A signal isn't something you need to move pixel-by-pixel at $c$.

It is:

```
emission event
position
time
direction / beam
spectrum
information payload
```

plus a lightlike trajectory.

To determine when another moving ship receives it, solve:

$$|x_{\rm receiver}(t)-x_{\rm emission}|=c(t-t_{\rm emission})$$

For piecewise-linear ship trajectories, that's basically a quadratic solve.

So:

> **signals don't update either.**

They exist geometrically in spacetime.

The same applies in reverse when rendering.

At observer event

$$O=(x_o,y_o,t_o),$$

you don't ask:

> Where is Alpha now?

You ask:

> Where does my past light cone intersect Alpha's worldline?

That intersection gives the state you actually observe.

Your entire sensor system can therefore emerge from **past-light-cone queries against worldlines**.

That is incredibly aligned with the game.

The engine should have a simulation coordinate time $t$. Choosing a coordinate system doesn't violate relativity; it's just how you label events.

Your proper time along your worldline is derived from it.

For inertial motion:

$$d\tau = dt\sqrt{1-\frac{v^2}{c^2}}$$

So perhaps:

```
player experiences      8 years
external world          80 years
```

But a planet with an analytical orbit doesn't suddenly require 80 years worth of frames.

You evaluate:

```
state_at(t + 80 years)
```

once.

A dormant NPC scheduled to arrive somewhere in 62 years generates its arrival event.

A civilization might generate 147 economically/politically meaningful events during those 80 years.

Those 147 events cost computation.

The other billions of seconds don't.

Therefore:

> **runtime should scale primarily with causal events and prediction invalidations, not simulated elapsed time.**

That is probably the single most important engine principle.

# And $c$ gives you something even better: free parallelism

This might be one of the strongest consequences of your physics choice.

If two regions are 10 light-years apart, nothing one does _now_ can causally alter the other for 10 years.

That gives the simulator **lookahead**.

Region A can safely simulate forward for some interval knowing that region B cannot surprise it before a calculable lower bound.

This is closely related to conservative parallel discrete-event simulation: if a subsystem knows a lower bound on when another subsystem can next affect it, it can advance independently without rollback. “Lookahead” is one of the central mechanisms used in these algorithms. [ResearchGate+1](https://www.researchgate.net/publication/228970039_Lookahead_Accumulation_in_Conservative_Parallel_Discrete_Event_Simulation?utm_source=chatgpt.com)

Your game has a physically meaningful lookahead built into the universe:

$$\Delta t_{\min}\geq \frac{d}{c}.$$

Ships are slower than $c$, so information is normally the worst case.

That means you can partition the universe spatially and have workers process different regions asynchronously up to their **causal safe horizon**.

That's a direct computational benefit from relativity.

Beautifully, FTL would destroy much of it.

# The “infinite” universe and gravity can share one hierarchy

I think there's another major architectural win here.

Make the universe a huge deterministic hierarchical quadtree generated from a seed.

Conceptually:

```
Universe seed
       │
       ├──────────────┬──────────────┬──────────────┐
       │              │              │              │
   quadrant        quadrant       quadrant       quadrant
       │
      ...
```

At every node store only coarse descriptors:

```
mass
center of mass
multipole moments

luminosity
spectral summary

resource statistics

generation seed
bounding box
```

Then this _same hierarchy_ can power three different things.

**World generation.** Far regions exist only as coarse deterministic nodes. Refining a node deterministically reveals systems, planets, resources, etc.

**Gravity.** Distant nodes are used through their multipole moments. Nearby nodes get opened.

**Rendering/sensors.** A distant node may render as one luminous feature. Zooming or gaining sensor resolution opens it.

That's extremely attractive.

Far away:

```
[ one node ]
M
COM
quadrupole
luminosity
```

Closer:

```
         node
       / / \ \
      * *  * *
```

Closer again:

```
stars → planets → ships
```

You don't need to instantiate the leaves unless something demands them.

Fast multipole methods can reduce long-range N-body force evaluation toward $O(N)$, while tree methods typically achieve $O(N\log N)$, by replacing sufficiently distant groups with multipole representations. [PubMed Central (PMC)+1](https://pmc.ncbi.nlm.nih.gov/articles/PMC2634295/?utm_source=chatgpt.com)

In your case I'd initially choose a Barnes–Hut-like tree because it's much simpler, then test whether FMM earns its complexity. The literature itself notes that better asymptotic complexity doesn't automatically mean faster implementations for practical $N$. [J-STAGE](https://www.jstage.jst.go.jp/article/journalam1998/2/0/2_0_101/_article/-char/en?utm_source=chatgpt.com)

# There's a subtle generation problem to solve

If I look at a distant region and use:

```

COM = ...
quadrupole = ...
```

and then later zoom in and generate its stars, those generated stars must reproduce the coarse gravitational representation.

Otherwise merely **observing the universe changes its gravity**.

That's unacceptable.

So hierarchical generation should conserve its parent's moments.

One interesting scheme is essentially a procedural wavelet:

```
parent mass distribution
        ↓
generate 4 children

Σ M_child = M_parent

Σ M_child x_child = M_parent x_COM

higher-order residuals constrained appropriately
```

Further refinement adds finer-scale structure while preserving coarse structure.

Then generation LOD is physically invariant.

That's much harder than Minecraft chunks, but also much more principled.

For the MVP, you can cheat by making a ludicrously large finite root domain—say far larger than anything reachable in millions of gameplay years—so it's “infinite” operationally without requiring actual mathematical infinity.

# Gravity should have modes too

I would not make every entity participate in the same N-body integrator.

Most ships have completely negligible gravitational influence. They're test particles.

Most planets are dominated by their star.

Most moons are dominated by their planet.

So:

```

→ feels gravity
→ does not contribute meaningfully to global gravity

planet
→ contributes
→ usually analytically propagated around star

star
→ contributes strongly
→ system barycentric dynamics

dense stellar encounter
→ full local N-body
```

That alone eliminates enormous work.

Use the analytic dominant solution:

$$\text{exact two-body motion} + \text{small perturbation}.$$

Compute the perturbation, not the whole motion.

That's the same philosophy you've used successfully elsewhere: remove the large known structure and spend compute only on the residual.

# Adaptive precision should be error-driven

I would explicitly attach an error budget to trajectories.

For example:

```
trajectory prediction valid while

position_error < εx
velocity_error < εv
proper_time_error < ετ
```

The tolerances can depend on context.

A star 50,000 ly away can have kilometers or much more of positional error without affecting anything.

Two docking ships may need centimeter precision.

For multipoles, choose expansion/opening based on requested force error.

For trajectory integration, choose timestep based on local error.

For rendering, choose detail based on projected screen-space error.

This produces one general rule:

> **precision is purchased only where an error could change an observable or causal outcome.**

That is better than a fixed hierarchy such as Newtonian below `0.1c`, approximation until `0.5c`, etc.

Also, I wouldn't obsess about replacing square roots with Taylor series yet. On modern CPUs/GPUs, avoiding **billions of evaluations entirely** will dwarf the gain from replacing one `sqrt`.

The hierarchy matters orders of magnitude more than arithmetic micro-optimization.

Yes. The architecture is getting sharper. I think the phrase we want is no longer merely **continuous-time spacetime engine** but:

> **an error-bounded causal spacetime engine**

The universe is a deterministic program over spacetime. We evaluate only the pieces required to certify what can happen, what did happen, and what the player can know. Player actions are perturbations; everything downstream is incremental recomputation.

That framing connects an astonishing number of mature ideas from computational geometry, celestial mechanics, hybrid systems, HPC and discrete-event simulation.

First, the 2D question: no, I don't think you need three spatial dimensions.

You need two spatial coordinates, $x,y$, plus time. Computationally that gives you a 2+1-dimensional spacetime in which trajectories are curves and interactions are geometric intersections. But I would **not** use literal 2+1-dimensional general relativity. Actual GR in 2+1 dimensions is qualitatively different: vacuum gravity has no local propagating gravitational degrees of freedom. [arXiv](https://arxiv.org/abs/gr-qc/0409039?utm_source=chatgpt.com)

Instead the game can be:

> **2D kinematics embedded in familiar 3+1-derived physics.**

Set $z=0$. Bodies remain in a plane. Use the familiar GR/PN gravitational laws restricted to planar trajectories. Around a Schwarzschild/Kerr-like body you can use equatorial geodesics. You get the physics you intuitively mean by “relativity,” without storing a third spatial coordinate or rendering a 3D universe.

That is not a hack in the bad sense. It is choosing the physical model that serves the world.

The really important thing you noticed is **error**.

I think nearly every optimization decision should reduce to:

> What error does this approximation introduce, and can that error possibly change anything that matters?

But there is a trap: there cannot be one global scalar “error.”

For this engine I would distinguish at least:

$$\epsilon = (\epsilon_\text{field}, \epsilon_\text{trajectory}, \epsilon_\text{event}, \epsilon_\tau, \epsilon_\text{observation}, \epsilon_\text{branch})$$

because errors have radically different consequences.

A planet being 30 meters away from its “perfect GR” location after 600 years may be utterly irrelevant.

But getting the order of two political messages wrong by 0.1 seconds could theoretically produce a different discrete decision.

Likewise a gravitational solver can preserve energy beautifully while still accumulating the wrong secular orbital phase. This isn't hypothetical: Rein et al. showed that energy error alone can make a planetary integrator appear much more accurate than it really is; secular-frequency errors and artificial apsidal precession can remain despite dramatically smaller energy error. [arXiv+1](https://arxiv.org/abs/1908.03468?utm_source=chatgpt.com)

So I would set a hierarchy of sacred things:

**causal topology > discrete branch decisions > event times/proper times > physically relevant phase > exact positions > visual accuracy.**

If two worldtubes provably cannot meet, approximation is free.

If an approximation might change whether they meet, refine.

If two events might swap order and that order affects an agent's decision, refine.

If a distant planet's rendered position shifts by 0.02 pixels, who cares.

This points directly to one of the best exemplars I found: **Shewchuk's adaptive exact predicates**. In computational geometry, the expensive thing isn't obtaining lots of decimal digits; it's getting the _sign_ of an important predicate right. His algorithms start cheaply and only increase arithmetic precision when a result lies too close to zero to certify its sign. [CMU School of Computer Science+1](https://www.cs.cmu.edu/~quake/robust.html?utm_source=chatgpt.com)

That is almost exactly what Emergent Space wants.

Suppose some event is controlled by

$$g(s)>0.$$

Don't compute $g$ to absurd precision everywhere. Compute an interval

$$g(s)\in[g_-,g_+].$$

If $g_->0$, certified yes.

If $g_+<0$, certified no.

If

$$0\in[g_-,g_+],$$

then—and only then—spend more computation: higher multipole order, shorter integration segment, more precision, more detailed local state, etc.

So instead of “LOD,” I think your engine wants **proof refinement**.

That leads to another field which is almost eerily close to what you're describing: kinetic data structures.

A KDS doesn't continuously recompute a moving configuration. It keeps cheap **certificates** saying the current combinatorial state is valid, predicts when those certificates will fail, and only does real work at those failure events. Guibas's description is literally: moving objects vary continuously, but the interesting combinatorial structure changes only at discrete moments; cached assertions certify correctness until one fails. [Stanford Graphics](https://graphics.stanford.edu/courses/cs428-03-spring/Papers/readings/CollaborativeProcessing/guibas_KDS_Handbook.pdf?utm_source=chatgpt.com)

Your Saturn→Venus ship therefore shouldn't be:

```

velocity
update interval
```

It should be closer to:

```

t0 .. t1
generator
error envelope

CERTIFICATES
no collision before t1
target interception remains feasible
no relevant signal arrives before t1
gravitational approximation remains valid
no sensor threshold crossed before t1
```

Until one of those certificates expires, the ship doesn't exist computationally as an “active thing.”

That's considerably stronger than adaptive timesteps.

And hybrid-systems research gives us the rigorous version of your tube idea. Tools such as Flow* build **flowpipes**: guaranteed enclosures of all states a nonlinear continuous system can occupy over a time interval, with adaptive timestep and approximation order, and then test whether those tubes intersect transition guards. [home.cs.colorado.edu](https://home.cs.colorado.edu/~srirams/papers/cav2013-flowstar.html?utm_source=chatgpt.com)

That is a beautiful primitive for this engine:

If it overlaps a potential interaction, tighten it.

If tightening still leaves ambiguity, promote that region to the expensive solver.

This is probably the correct generalization of your “things should update based on acceleration” thought. The true criterion is not acceleration.

It's:

> **How long can I certify the current model before its uncertainty becomes capable of altering a consequential predicate?**

That can sometimes be millions of years.

It's a boundary-value problem:

For simple regimes this can be solved analytically or semi-analytically. In weak-field interplanetary flight, Lambert-type problems already have exactly this character: meet a moving target at a future point rather than chase its current position.

> **Replace a large set of causes by the smallest certified summary sufficient to bound their effect on the current query.**

Multipole is one instance.
